# 长时数值压力测试记录

> 目的：回答一个具体问题——**小镇在一段很长的游戏时间里，会不会出现某个数值崩掉、或者永远涨下去、或者卡死救不回来**。方法是用脚本按固定步长把模拟跑到数小时级别，检查每一个可观察量是否始终落在自己的边界内，并把发现的问题修掉。
>
> 本文记录的是实测数据与结论，不是设计意图。

## 一、测试方法

脚本以 0.5 秒为步长直接驱动 `SimWorld.tick`，覆盖三种情境：

| 情境 | 设定 | 用途 |
| --- | --- | --- |
| 无操作 | 不做任何决策，灾害开／关各跑一遍 | 检验"放着不管"会不会崩 |
| 自动副官 | `autoMayor` 开启（会修缮、清仓、交付订单、派商队） | 检验现有自动化能否维持 |
| 积极照看 | 修缮 → 收货 → 保口粮 → 卖余量 → 建住房／食物设施 | 检验"正常玩家"能否持续推进 |
| 极端疏忽后接手 | 税率拉满、零操作跑 8 小时，再积极照看 | 检验最坏存档能否救回来 |

每一步都断言：金币与声望非负且有限、幸福度与四项需求在 0–100、人口在 4 与人口上限之间且为整数、库存总量不超过仓储上限且各项为非负整数、建筑进度在 0–1、建筑等级在 1–3、日志长度有界。

## 二、结论：稳态健康

积极照看 5 小时（灾害开启）：

```
第 5 天   金币 12102  人口 18 幸福 79 环境 75 木材 56  库存 130/240
第 10 天  金币 41148  人口 18 幸福 72 环境 75 木材 54  库存 187/240
第 30 天  金币 110045 人口 18 幸福 83 环境 95 木材 36  库存 235/240
```

无灾害对照 5 小时，人口 12 → 25、金币 32069。**没有崩盘，也没有失控**：金币线性增长（税收驱动）、人口稳定在住房上限、库存长期贴近上限但被市长的清仓规则压住。

灾害压力与偿付能力（开局小镇实测）：

| 指标 | 数值 |
| --- | --- |
| 单次灾害平均修缮成本 | 70 金币、2.0 木材、1.8 石料 |
| 灾害间隔 | 420 秒（8.6 次/小时） |
| ⇒ 灾害带来的每小时开销 | 约 600 金币、17 木材、15 石料 |
| 开局小镇每小时税收 | 约 1640 金币 |
| 开局小镇每小时木材产量 | 约 900 木材 |

**良性小镇完全撑得住灾害**，不需要调整灾害频率。

## 三、修掉的四个真实缺陷

测试的价值全在这四条上。前两条是**不可恢复的死局**，后两条是**劳动力被永久浪费**。

### 1. 木材归零 + 产木建筑全损 = 存档终结

最坏情境（8 小时无照看）会出现：木材 0、石料耗尽、19 座建筑中 16 座受损。此时**游戏内不存在任何取得木材的动作**：

| 尝试 | 结果 |
| --- | --- |
| 从还立着的建筑收货 200 秒 | 木材 +4（仅花园等，且不持久） |
| 交付现有订单 | 木材 0（订单给金币与建材，不给木材） |
| 商队往返 | 木材 0 |
| 出售余量 | 木材 0 |
| 建锯木场／林场 | 需要木材 ×10 起 |
| 修缮一座建筑 | 需要木材 ×1 起 |

即"修缮要木材，产木材要先有木材"。而**离线报告的存在说明"玩家离开"是被支持的正规场景**，离开后存档变成不可恢复，是真实缺陷。

修复：`repairQuote()` 让修缮短缺的材料以金币现买（木材 45、石料 55 一份），价格高于自行生产，因此是脱困手段而非套利手段。修缮从此只受金币限制。

### 2. 伤员越多的镇子被打得越狠，永远追不上

修缮需求随受损建筑数**线性增长**，而收入随停产建筑数**下降**。两者叠加是一个发散的反馈：落后的小镇以与修缮相同的速度被再次打击，永远无法收敛。实测：接手 5 小时后仍有 13 座受损、木材为 0。

修复（三重，均只影响已经出事的小镇）：

| 规则 | 作用 |
| --- | --- |
| `damageCeiling()`：同时受损不超过建筑总数的 1/3 | 越过上限则**完全不触发**新灾害 |
| `strikeInterval()`：间隔按受损比例拉长（最多 ×7） | 受损越重，喘息越久；健康小镇（受损 0）间隔不变，仍是 420 秒 |
| `MIN_DISASTER_POPULATION = 10`：人口低于 10 不触发灾害 | 灾害是对**运转中的小镇**的压力，不是补刀；残破小镇无人可失、也无收入可修 |

修复后实测：疏忽 8 小时 → 受损 1 座（上限内）；接手 10 小时后人口 4 → 24、幸福度 15 → 85、受损 0、食物恢复流通。**死局消除，且已写成测试。**

### 3. 人手分配按建造顺序，小城镇把工人派给不干活的作坊

原实现按建筑顺序分配工人。4 个人口的镇子会把人手全给磨坊与面包房（面包房因缺面粉而不出产），**渔场——唯一不耗原料就能产食物的建筑——一个人也分不到**。没有食物 → 人口不涨 → 永远没有额外人手，形成自锁。

修复：人手分配改为按**镇子是否需要**排序，且仅在**真的缺粮**时启用：

- 粮食链优先于材料，材料优先于其他；
- 同类中"不需要原料"的排前面（渔场 → 磨坊 → 面包房）；
- 同类中"有料可开工"的排在"等料"的前面，避免把工人停在空转的作坊。

**已吃饱的小镇完全保持原有人手分配**，玩家的产业链不会被抢人（这条也有测试守着）。

### 4. 工人数一旦被清零就再也回不来

`reconcileWorkforce` 原先取 `building.workers ?? maximum`——`workers` 为 `0` 时不是 `null`，所以**曾被削减到 0 的作坊永远是 0**，即使后来有了空闲人口。人口下降是全自动的，玩家没有参与，却造成了永久损失。

修复：

- 改为从作坊的编制人数重新分配（`staffing ?? maximum`）；
- 新增建筑字段 `staffing`：玩家用"人手"按钮显式设定的编制会被**钉住**，小镇重新分配时不动它。系统自动分配与玩家意图从此是两件事，不再互相覆盖；
- 人手分配**每天重算一次**（原先只在人口变化时重算），因为"谁还能干活"随修缮与库存变化，只在户口变动时重算会长期停留在过时的分配上。

> 附带修正：六个既有测试夹具用 `b.workers = 0` 表达"这些作坊没人干活"。在新模型下这必须写成 `b.staffing = 0`，否则小镇会（正确地）把它们填满。夹具已同步。

## 四、声望经济：测出来之后怎么改的

压力测试量出声望严重超发（供给 228、唯一去处研究 26）。当时只记录未改，因为改法需要玩家体验来判断。后续做了专项实验，结论如下，并据此改了数值。

### 4.1 实验一：声望到底卡不卡人

把研究价目整体放大 k 倍，跑同样的五小时，看「被声望卡住」何时出现：

| k（研究价目倍数） | 学到的科技 | 在手声望 | 卡点分布 |
| --- | --- | --- | --- |
| ×1（原值，26） | 5/8 | 54 | 等级 3 · 材料 177 · **声望 0** |
| ×2（52） | 5/8 | 37 | 材料 167 · 等级 2 · **声望 11** |
| ×4（104） | 5/8 | 9 | **声望 179** · 等级 1 |
| ×8 | 3/8 | 7 | **声望 180** |
| ×32 | **0/8** | 62 | **声望 180** |

两个关键结论：

1. **×2 是最小的、开始生效的倍数**，而且**不拖慢进度**（五小时同样学到 5/8）。×4 起进度开始受损，×32 完全卡死。
2. 研究实际被**材料**卡住（材料需求合计只有 30，且商队与建材坊都能产），不是被声望卡住。声望在 ×1 时覆盖率是 **0**。

因此把研究声望价目**整体 ×2（26 → 52）**：这是最保守的一手，让货币有存在感，同时经实测不改变进度节奏。

### 4.2 实验二：光抬价不够，还需要出口

即使价目 ×2，一个把成就、街区风格、故事都做完的玩家最终仍会有约 **180 点声望**没有用处——**总量**过剩的问题不会因为抬价而消失，只会推迟。

于是新增**小镇荣誉**（`src/sim/honours.ts`）：三条线各四级，一级比一级贵，效果永久保留。

| 荣誉 | 效果（满级） | 价目 |
| --- | --- | --- |
| 仓廪扩建 | 仓储容量 +32 | 6 / 9 / 13 / 18 |
| 精工传承 | 生产时间 −6% | 6 / 9 / 13 / 18 |
| 安居名额 | 社区人口名额 +8 | 6 / 9 / 13 / 18 |

全部买满 138 点，与研究 52 相加为 190，与全部固定来源 228 同量级——**货币总量重新对得上**。三档效果都刻意做小（仓储 +32 相对 240 起点、生产 −6% 相对已有的 −10% 科技与 −5% 称号、名额 +8 相对 12 基础），是**缓解**已有压力而不是取消它们。

### 4.3 门禁：为什么按等级而不是按科技

初版把三条荣誉挂在 `logistics`／`efficiency`／`civics` 之后，实测**一次都没买出去**：这三项科技本身需要 tools／cloth／clothing，也就是要么等一条完整的纺织与冶炼产业链。结果是**出口被锁在产业链尽头**，而锁住链条的是**材料**，恰恰又问不到声望。

改为按**小镇等级**开放（5／6／7 级）。等级是任何玩法都会到的东西，于是每一种玩家都能把声望花出去。

### 4.4 改后实测

五小时、同一套称职策略，只切换「是否购买荣誉」：

| 情形 | 等级 | 科技 | 在手声望 | 研究花费 | 荣誉花费 | 购买次数 |
| --- | --- | --- | --- | --- | --- | --- |
| 不买荣誉 | 25 | 5/8 | 40 | 28 | 0 | 0 |
| 买荣誉 | 25 | 5/8 | **0** | 28 | 36 | 5 |
| 买荣誉（十小时） | 36 | 5/8 | 1 | 28 | **71** | 8 |

在手声望从 40 降到 0–1，**声望真正被花掉了**。五小时能买到 5–8 级（占 12 级的 42%–67%），买满需要更长时间，因此不是一个可以立刻清空的清单。

### 4.5 一个被测试抓到的实现缺陷

荣誉面板最初把「已购买级数」显示成 **6 / 4**。原因是 `honourSummary` 返回的 `level`（已买级数）与荣誉定义里的 `level`（开放等级）在同一对象里被后者覆盖。已把定义里的字段改名为 `unlockLevel`，并在测试里断言 `level <= max`，避免两者再次混淆。

## 五、未改动、但有记录的现象

- **库存长期贴近上限**（约 235/240）。这是清仓规则在起作用而非故障：`sellSurplus` 只卖超出保留量的部分，保留量本身接近上限。玩家会看到仓库常满，属于设计现状。
- **金币线性增长无上限**，5 小时 11 万。税率与订单是主要来源，没有发现通胀对玩法造成压力（建筑价格是固定的），因此未动。
- **人口稳定在住房上限**（无灾害 25、有灾害 18–24），由住房容量决定，符合"人口 = 床位"的设计。
- **修缮窗口内人口会短暂高于当前容量**：住房容量有意排除受损建筑（受损的房子住不了人），而修缮需要 30 秒，这段时间里"当前容量"低于人口。这是设计行为而非越界——人口增长条件是 `population < 容量`，受损期间只是停止增长，不会把居民赶走，修缮完成后容量自动回升。判据应取"全部建筑完好的容量"，测试脚本与 `tests/balance.test.ts` 都按此口径断言。
- **自动副官很能干**：开启后 5 小时人口 18、金币 12 万、23 级，且不会研究科技（副官不做研究），因此"研究"仍是玩家的事。

## 六、回归测试

新增 `tests/balance.test.ts`（13 项）把上述结论固化下来：

| 测试 | 守住的契约 |
| --- | --- |
| 修缮不被无法生产的材料卡住 | 死局不再出现；现买价格 = 基础价 + 溢价 |
| 有料时不收溢价 | 安全阀不等于涨价 |
| 溢价高于材料价值 | 不能靠清空仓库来买便宜木材 |
| 损伤有上限 | 任何规模的镇子都有上限，且不超过 1/3 |
| 受损越多间隔越长、健康时不变 | 反馈从发散改为收敛 |
| 人口过少不触发灾害 | 残破小镇不被补刀 |
| 废墟能恢复 | 疏忽 8 小时 + 照看后，受损归零、幸福回升、金币为正 |
| 小城镇先保住食物 | 缺粮时渔场优先获得人手 |
| 吃饱的城镇不被人手重排 | 玩家产业链不被抢人 |
| 空闲人手不会永久丢失 | 归零的作坊能被重新填满 |
| 玩家钉住的编制不被改动 | 显式意图优先于自动分配 |
| `staffing` 字段照常校验 | 坏档拒绝 |
| 十小时无操作不越界 | 所有可观察量始终在边界内 |

另外，`tests/industry.test.ts` 中的迁移测试覆盖同一轮发现的存档读取缺陷（见下节）。

全套测试 260 → 273 项（另见下一节：存档修复与开局时刻各 +1，共 276 项）。

## 七、同一轮发现：旧存档无法读取

压力测试的浏览器验证阶段出现「自动存档已保护」，追查后确认是一个**会让玩家丢档的缺陷**，与数值无关但同样属于「长时运行才会暴露」的一类。

现象：某份 v2 存档在启动时被拒，游戏进入保护状态，小镇无法载入。

根因：该存档写于「牛奶/奶酪/蜂蜜/葡萄/葡萄酒/陈酿」加入之前，`resources` 只有 16 个键；而 `validateSave` 要求 `RESOURCE_KEYS` 全键齐备，缺键即判为损坏。`migrateSave` 本就有补齐逻辑（`{ ...emptyResources(), ...value.resources }`），但**只在 `version === 1` 分支里**，v2 存档直接落到 `version !== 1 → return null`。结果：任何较早版本写下的 v2 存档，在此后新增资源的版本里都无法再读取。

修复：迁移增加 v2 分支，资源与统计计数按空缺补齐后再校验；只补空缺、不修错值，因此负数、小数、未知资源名、非数值计数依然一律拒绝。`stats` 的九个计数抽成一份共用清单，避免以后再次出现「校验要求但迁移不补」。

验证：原先无法读取的真实存档现在正常载入，状态栏由「自动存档已保护」变为「刚刚已保存」，等级、居民数、金币与库存全部保留，写回的存档已含全部 22 个资源键。
