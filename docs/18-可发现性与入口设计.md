# 18 · 可发现性与入口设计

> 本文记录一个具体的界面问题：**功能存在、数值配平、但玩家找不到**，以及为此检索到的外部指引与落实方式。
>
> 起因：荣誉系统（《15》第四节、《17》第三节）修好数值之后，Idle Idol 的复盘留下一条警告——「感觉慢」未必是数值问题，可能是入口太难找。本文就是去验证并处理这一条。

## 一、问题：功能在，但没有人会走进那个房间

先量清楚事实，不靠感觉：

| 事实 | 数值 |
| --- | --- |
| 荣誉区块在科技面板中的位置 | 面板 HTML 起始于第 71924 字符，荣誉区块调用在第 74821 字符——**在所有科技卡片之后** |
| 指向科技面板的入口数量 | **1**（底部 dock 的「科技」按钮；顶部声望数字也指向同一面板） |
| 荣誉**开放时**的任何提示 | 无 |
| 荣誉可购买时的任何提示 | 无 |

问题不只是"在最底部"。真正的失效在于**面板的心智模型**：它叫「科技」，作用是研究；一个把 8 项研究学完的玩家**再也没有理由打开它**——而那恰好是荣誉最该被使用的时候（5 级开放，8 项研究通常在此之后完成）。功能被放在玩家已经办完事的房间里。

这一条在文献里有正式名称与描述：

> **"Multiple layers can confuse users and make finding 'buried' functionality hard."**
> —— IxDF，Progressive Disclosure，Best Practices 一节

> **"The end of the road** — What happens when all features are unlocked? Is the game then beaten?"
> —— ui-patterns.com，Unlock Features，Discussion 一节

## 二、检索到的指引

### 2.1 渐进披露（Progressive Disclosure）

**来源**：Interaction Design Foundation（IxDF），Progressive Disclosure。
<https://ixdf.org/literature/topics/progressive-disclosure>

定义：把高级功能延后到次级界面。但同一页的 **"Guide the User"** 一节给出的，正是本问题的解法：

> **"Make it clear where advanced functions are available.** To achieve clarity, use icons, labels, and other **signifiers**. These signifiers suggest there's more information available."

> **"Implement feedback mechanisms.** Use prompts and feedback to guide users in discovering and using hidden features. For example, a user completes a task for the first time in an application. **A prompt might appear to congratulate them and suggest a related advanced feature they have yet to try.**"

> **"Keep important information visible."**

同页另有一条**约束**，决定了我不该做什么：

> **"Avoid multiple access paths.** Users can become confused if they can reach the same information or feature in several ways. **A single straightforward path is better for usability.**"

—— 所以**不加第二个入口**，而是把现有那一条路变得更明确、落点更好。

同页还警告了与本例相关的失效模式：

> **"When 'advanced' features become everyday tasks"** the benefits of progressive disclosure diminish…

> **"Dumbed-down content** — …a photo editing application's UI may be easy to understand, but the software's full range of features and tools are **challenging to find**. Designers must find the balance between **usability and discoverability**."

### 2.2 解锁功能（Unlock Features）

**来源**：ui-patterns.com，Unlock Features 设计模式。
<https://ui-patterns.com/patterns/Unlock-features>

> **"The end of the road** — What happens when all features are unlocked? Is the game then beaten? Or can you make your rewards variable? … **Design your end state so that the experience you have built will be enjoyable even with all features unlocked.**"

该模式还指出解锁会与**禀赋效应**（Endowment Effect）配合：

> "Unlocked capabilities act as **endowments** that will lock your users into valuing your website more than before they signed up."

对本作的含义：荣誉是**已解锁但未被使用**的禀赋。玩家看不到它，就等于感觉不到这份禀赋。

### 2.3 Idle Idol 的教训（回顾）

**来源**：Gabriel Padinha，《Balancing Tips: How We Managed Math on Idle Idol》，Game Developer，2020-07-09。
<https://www.gamedeveloper.com/design/balancing-tips-how-we-managed-math-on-idle-idol>

> "The 'game is too slow' problem was a huge hit to our balancing… **Wrong.** Another feedback that was not taken into account was that the passive skills screen was **hard to find and not well explained**… the game would feel very slow, but not because of the curve of balancing, but rather because the players **weren't interacting with a crucial feature**."

这条决定了本次的优先级：**先证明入口能被找到，再谈数值**。

## 三、落实：四处改动，全部来自上面的指引

| 指引 | 落实 |
| --- | --- |
| IxDF「use icons, labels, and other **signifiers**」 | dock 的「科技」按钮在**有可买荣誉时**显示角标计数 |
| IxDF「**Keep important information visible**」 | 面板顶部台账同时报告研究与荣誉进度，不必滚到底部 |
| ui-patterns「**the end of the road**」/ IxDF「feedback mechanisms… **suggest a related advanced feature**」 | 研究学完的那一刻，面板顶部出现指向荣誉的提示条，并写一条日志 |
| IxDF「**a prompt might appear to congratulate them**」 | 升到某条荣誉的开放等级时，升级日志一并说明该荣誉可以投入声望了 |

### 3.1 顺手修掉两个"哑"角标

dock 的角标机制本来就存在，且代码里已经为 `quests`、`caravan`、`technology` 三个按钮预留了元素：

```js
for (const key of ['quests', 'caravan', 'technology']) {
  const n = key === 'caravan' ? Number(s.caravan.status === 'returned') : 0;   // ← 另两个恒为 0
  ...
}
```

即 `quests` 与 `technology` 的角标**永远是隐藏的**——基础设施在那儿，什么也没说。现在三个角标各自回答"这里现在有没有东西给我"：

| 角标 | 含义 |
| --- | --- |
| 成长 | 有已完成但未领取的目标 |
| 商队 | 商队已归来 |
| 科技 | **声望足够买下的荣誉条数** |

## 四、实现要点

### 4.1 徽标必须能在渲染路径里廉价计算

界面每帧都会更新角标，而 `observe()` 会重算需求并跑一遍所有进度同步（成就、风格、故事），**不能放在渲染路径里**。因此新增两个纯函数（`src/sim/honours.ts`）：

```ts
affordableHonours(progress, prestige, level)   // 已开放 + 未满级 + 买得起 的条数
honourLevelsTaken(progress)                    // 三条线共买了几级，供台账显示
```

两者都只读参数、不触状态，既有单测也有"徽标数字等于实际可买次数"的一致性断言。

### 4.2 两条公告必须只响一次，且各有明确的触发条件

- **升级公告**：写在升级循环内，条件是该等级**恰好等于**某条荣誉的开放等级。因此每条线只响一次，且不会因为继续升级而重复。
- **学完公告**：写在 `research()` 内，条件是 `researched.length === TECHNOLOGY_KEYS.length`——只会在最后一次研究时成立。

两者都不需要新增存档字段：触发条件都能从既有状态推出。

> 测试过程里踩到一个坑并已修正：升级日志每行都含"声望"（「获得 1 点声望」），所以**不能用"含声望"当公告的判据**，否则每次都匹配。判据改为"含『科技面板』"——即公告独有的标记。同时因为日志有上限（60 条）会被淘汰，断言写成了"同一条线不会被公告两次、且不会公告未开放的线"，而不是脆弱的计数相等。

### 4.3 没有做的事

- **没有加第二个入口**。顶部声望数字与 dock 按钮都指向同一个科技面板，符合 IxDF「avoid multiple access paths」。改动是让那条唯一的路径**有信号**（角标）、**落点可见**（顶部台账）、**终点有指引**（学完提示条）。
- **没有做开场教程或强制弹窗**。本作定位是"没有催促"（见《01》《12》），因此只用常驻角标 + 一次性日志，不打断玩家。

## 五、验证

**测试 292 → 296 项**，新增 4 项：

| 测试 | 守住的契约 |
| --- | --- |
| 徽标数字回答"我现在能买吗" | 未开放／买不起／已满级都不计入；且徽标数字 == 实际可买次数 |
| 台账统计三条线累计级数 | 含坏档钳制 |
| 开放时公告、且每条线只公告一次 | 升级公告恰好对应已开放的线；继续游玩不重复 |
| 学完研究后指向声望去处 | 只响一次，且点名荣誉 |

## 六、仍未验证的一条

**真实玩家的眼动与行为**。本文证明了「入口存在信号、面板有指引、公告在正确时机出现」，但**没有证明玩家会看到**——这需要真人测试或埋点，不是我能替你判断的。

若要继续收敛，可测的指标是 IxDF 列出的那几个：**任务完成率**（荣誉首次购买的达成率）、**time on task**（从开放到首次购买的时间）、以及**到达率**（有多少玩家在 20 级前从未打开过荣誉区）。当前没有埋点设施，这是一个明确的、独立的后续项。
